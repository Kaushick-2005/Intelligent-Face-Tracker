# Sample Output and Database Verification

This document provides sample verification records generated by the **Intelligent Face Tracker** across MongoDB, SQLite, local event logs, and filesystem archives.

---

## 1. Database Schema & Sample Records

The following clean sample was generated by deleting the previous generated
event log and crop images, then processing these three videos completely:

| Video | Frames | Detections | Unique visitors | ENTRY | EXIT |
|---|---:|---:|---:|---:|---:|
| `record_20250620_183903.mp4` | 1502 | 2958 | 15 | 16 | 16 |
| `record_20250620_184049.mp4` | 1502 | 1998 | 9 | 13 | 13 |
| `record_20250620_184302.mp4` | 1502 | 1600 | 4 | 5 | 5 |

The lifecycle total can be greater than the unique-identity total when a
visitor leaves and later re-enters. The database total is persistent state
across earlier runs and is not the number of people in an individual video.
The third video reused existing identities `VISITOR_0057`, `VISITOR_0056`,
`VISITOR_0095`, and `VISITOR_0090`; it did not create a new visitor record.

### A. Visitors Collection / Table (`visitors`)
Contains unique enrolled visitors with facial feature representations.

```json
{
  "visitor_id": "VISITOR_0099",
  "registered_at": "existing persistent record",
  "crop_image_path": "logs/registrations/2026-10-03/VISITOR_0099_registered.jpg",
  "embedding": ["512-dimensional ArcFace vector"]
}
```

### B. Events Collection / Table (`events`)
Logs every verified ENTRY and EXIT transition with frame indexing, timestamps, and crop references.

```json
[
  {
    "video": "record_20250620_183903.mp4",
    "frame": 1444,
    "timestamp": 57.683,
    "visitor_id": "VISITOR_0099",
    "event_type": "ENTRY",
    "crop_path": "logs/entries/2026-10-03/VISITOR_0099_entry.jpg"
  },
  {
    "video": "record_20250620_183903.mp4",
    "frame": 1492,
    "timestamp": 59.601,
    "visitor_id": "VISITOR_0099",
    "event_type": "EXIT",
    "crop_path": "logs/exits/2026-10-03/VISITOR_0099_exit.jpg"
  }
]
```

## 3. Local Filesystem Tree for Event Crops

```
logs/
├── events.log
├── entries/
│   └── 2026-10-03/
│       ├── VISITOR_0099_entry.jpg
│       └── ... other clean-run entry crops
├── exits/
│   └── 2026-10-03/
│       ├── VISITOR_0099_exit.jpg
│       └── ... other clean-run exit crops
└── registrations/
    └── 2026-10-03/
        ├── VISITOR_0099_registered.jpg
        └── ... other registration crops
```

The JPEG files above are repository-tracked sample entry, exit, and
registration crops. A newly registered visitor stores its first-seen crop
under `logs/registrations/YYYY-MM-DD/`; this is separate from lifecycle ENTRY
crops.
For this rerun, existing visitors with matching ENTRY crops had their
registration references repaired to local files in that folder. If no matching
crop exists, the original database path is retained and the next genuinely new
registration is written only after its crop file has been verified on disk.
The SQLite database contains 68 events for these three videos, and MongoDB
contains the same 68 events. MongoDB contains 104 registered visitors after
these runs; that number includes persistent visitors from previous runs.

## 4. New Video and Live RTSP Persistence

Every input mode uses the same persistence path:

1. InsightFace produces a finite 512-dimensional embedding.
2. The embedding is compared against registered visitors using guarded cosine
   similarity. The default threshold is `0.40`, selected from the measured
   similarity distribution to reduce duplicate IDs without blindly accepting
   weak matches. Invalid,
   mismatched, non-finite, or zero-norm vectors are rejected instead of
   creating a false match.
3. A new visitor is registered once, or an existing `VISITOR_XXXX` identity is
   re-used when the similarity threshold is met.
4. A successful ENTRY/EXIT crop is written under `logs/entries/YYYY-MM-DD/` or
   `logs/exits/YYYY-MM-DD/`.
5. The event is persisted to SQLite and, when MongoDB is connected, to the
   `events` collection. SQLite remains available if MongoDB is offline.

Process another video without changing the database configuration:

```powershell
python main.py --source video/new_video.mp4
```

Run an RTSP stream:

```powershell
python main.py --rtsp "rtsp://USER:PASSWORD@CAMERA_HOST:554/stream1"
```

Live events are visible while the process is running in both the SQLite
database and MongoDB (when connected), and in `logs/events.log`. A live stream
does not have a natural end; EXIT events are generated after the configured
inactivity timeout. Stop the process gracefully after the final person leaves
so the remaining active tracks can be flushed as final EXIT events.

The database write path reports an explicit error if neither SQLite nor
MongoDB accepts an event. An event is not recorded when its crop image cannot
be written, preventing database rows with missing images.

The optional dashboard prefers the configured MongoDB `visitors` and `events`
collections and displays a live-source indicator. If MongoDB cannot be reached,
or the connected MongoDB collections are empty while SQLite has data, it
automatically queries the local SQLite tables instead and displays a fallback
warning. This prevents an empty MongoDB connection from hiding valid local
records. The dashboard uses a text search for Visitor ID rather than a visitor
dropdown, plus date, video, and event-type filters.

## 5. Verification Commands

To query unique visitor count and verification records directly from SQLite:
```powershell
python -c "from src.database.db_manager import DatabaseManager; db = DatabaseManager(); print('Total unique visitors:', db.get_visitor_count())"
```

To query recent entry/exit events:
```powershell
python -c "import sqlite3; conn = sqlite3.connect('database/intelligent_face_tracker.sqlite3'); cur = conn.cursor(); print(cur.execute('SELECT event_type, visitor_id, video, timestamp FROM events ORDER BY id DESC LIMIT 5').fetchall())"
```
